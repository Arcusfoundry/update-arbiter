# Session — 2026-05-14: Uptime Dashboard → Update Arbiter v2.0.0

## TL;DR

Started with a broken "Uptime Dashboard" that opened as a series of MessageBox popups instead of a window. Ended with **Update Arbiter v2.0.0**: a unified GUI installer + uptime dashboard + non-elevated tray agent, all with read-back verification on every privileged write. The original v1.0.0 installer had been silently failing — that's why this morning's Windows Update forced reboot got through.

## The morning's incident

At 06:05:54 today, `MoUsoCoreWorker.exe` initiated a planned restart as `NT AUTHORITY\SYSTEM` for *"Operating System: Service pack."* 3.5 minutes later, `TrustedInstaller.exe` initiated another for *"Operating System: Upgrade."* Textbook Windows Update auto-reboot pair.

Belief was that Update Arbiter was installed and protecting the machine. It wasn't. Investigation found:

- `C:\ProgramData\ArcusFoundry\` did not exist
- The `Arcus Foundry Update Arbiter` scheduled task was not registered
- `HKLM:\SOFTWARE\Policies\Microsoft\Windows\WindowsUpdate\AU` did not exist
- `NoAutoRebootWithLoggedOnUsers` was not set
- The three `\Microsoft\Windows\UpdateOrchestrator\Reboot*` tasks were not present at all

### Root cause: v1.0.0 silent failure

`update-arbiter-1.0.0.ps1` sets `$ErrorActionPreference = 'Continue'`. When `Set-ItemProperty` silently failed (likely an earlier non-elevated invocation, or a Windows feature update reset), the script kept running and printed `[OK] Registry policies applied.` even though no keys were written. The `#Requires -RunAsAdministrator` directive only blocks the no-admin invocation; it does nothing for downstream write failures inside an elevated session.

### Secondary issue: Win11 26200+ moved the reboot logic

On newer Windows 11 builds (this machine: 26200, late 25H2-track), the three `UpdateOrchestrator\Reboot*` scheduled tasks are **gone entirely**. Microsoft has migrated reboot-trigger logic into `MoUsoCoreWorker.exe` and `TrustedInstaller.exe` direct invocation. The `NoAutoRebootWithLoggedOnUsers` registry policy still gates the modern path, so it remains the load-bearing protection. The task-disable half of v1.0.0 is increasingly belt-and-suspenders for code that no longer exists.

## What we built

### 1. Uptime Dashboard (interim — superseded)

`UptimeDashboard.ps1` / `.exe` — WinForms GUI showing boot/shutdown sessions correlated with:
- **USER32 / 1074** (user/process-initiated shutdowns, with reason text)
- **Microsoft-Windows-Kernel-Power / 41** (system not cleanly shut down)
- **BugCheck / 1001** (BSOD bugcheck codes)

Original popup problem was PS2EXE `-noConsole` mode redirecting `Write-Host` to `MessageBox.Show()`. Script had ~10 `Write-Host` calls, so 10 popups.

### 2. Update Arbiter v2.0.0 — admin GUI (`requireAdmin`)

`UpdateArbiter.ps1` / `.exe` (76 KB):

- **Status banner** — green/red dot, headline `PROTECTED` / `NOT INSTALLED`, version, install date, scheduled-task state, tray status
- **Sessions grid** carried from the dashboard work, with Reboot Reason column
- **Install modal** — confirm → streaming `RichTextBox` log with colored levels (`STEP` / `OK` / `WARN` / `FAIL` / `DONE`). Every registry write does `Set-ItemProperty` → `Get-ItemProperty` read-back compare. Final verification pass refuses to report success unless all policies are present and the self-heal task is healthy.
- **`-SelfHeal` mode** — bypasses GUI, applies lockdown silently, writes to `C:\ProgramData\ArcusFoundry\update-arbiter.log`. Scheduled task runs `UpdateArbiter.exe -SelfHeal` as SYSTEM on boot, logon, and `WindowsUpdateClient` events 19/43.
- **State file** `state.json` — records `Version`, `InstalledAt`, `InstalledBy`.

### 3. Update Arbiter Tray — non-elevated agent (no `requireAdmin`)

`UpdateArbiterTray.ps1` / `.exe` (42.5 KB):

- Notification-area shield icon — **green** = protected, **red** = degraded, **yellow** = check failed
- 5-minute polling timer reading HKLM policies + scheduled-task state (both readable without admin)
- Right-click menu: **Open Dashboard…**, **Verify Now**, **View Log**, **About**, **Exit**
- Single-instance mutex `Global\UpdateArbiterTray.SingleInstance`
- Autostart via `HKCU:\Software\Microsoft\Windows\CurrentVersion\Run\UpdateArbiterTray`, set by the installer
- Launched at medium integrity from the elevated installer via `Shell.Application.ShellExecute` (a plain `Start-Process` from an elevated parent inherits elevation and would force UAC at every logon)

## Key technical decisions

1. **Two EXEs, not one.** Admin GUI needs `requireAdmin`; tray must NOT have it (otherwise UAC at every logon). Single-EXE auto-elevation was considered and rejected as more complex without UX benefit.
2. **Read-back verification on every privileged write.** Replaces v1.0.0's `Continue` + blind success reporting. Captured as a feedback memory for future sessions.
3. **Treat missing `UpdateOrchestrator\Reboot*` tasks as expected on Win11 26200+.** Warn instead of failing; lean on `NoAutoRebootWithLoggedOnUsers` as the real block.
4. **Self-heal scheduled task runs the EXE with `-SelfHeal`**, not a copied `.ps1`. Runtime EXE-vs-PS1 detection via `[System.Diagnostics.Process]::GetCurrentProcess().MainModule.FileName`.
5. **Tray launch from elevated installer uses `Shell.Application.ShellExecute`**, not `Start-Process`. Avoids inheriting elevation into the tray child.
6. **MSI deferred.** For free download / SMB path, the EXE GUI installer is fine; cheaper wins are Add/Remove Programs registration (~30 lines) + EV code-signing. WiX MSI saved for the Sparkforge Pro / Fractional CTO fleet deployment workstream — at that point it can be a thin wrapper that shells out to `UpdateArbiter.exe -SelfHeal` rather than re-implementing install logic declaratively.
