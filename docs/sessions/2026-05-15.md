# Session — 2026-05-15: Tray-agent bug fixes (NotifyIcon limit + variable scope)

## TL;DR

Two small but blocking bugs in the v2.0.0 tray agent surfaced after deploy. Both fixed in `UpdateArbiterTray.ps1`, rebuilt, redeployed to `C:\ProgramData\ArcusFoundry\`. Tray now runs cleanly with green/red shield status. Tray version bumped to v2.0.2.

## Bug 1 — `NotifyIcon.Text` legacy 63-char cap

**Symptom:**

```
Exception setting "Text": "Text length must be less than 64 characters long.
Parameter name: Text
Actual value was Update Arbiter v2.0.0 - PROTECTED | since 2026-05-14 | checked 16:37.
```

**Root cause:** The WinForms `NotifyIcon.Text` property enforces the legacy `Shell_NotifyIcon` `NOTIFYICONDATA` 63-char limit. The modern 127-char limit only applies when an app opts into the v6 `NIF_TEXT` size, which the WinForms wrapper does not. My truncation helper had a 127-char cap inherited from the modern spec — wrong limit.

**Fix:**

1. Cap truncation at 63 chars (with 60 + `...` fallback).
2. Compact the tooltip to the essential signal only:
   - Protected: `Update Arbiter v2.0.0 - PROTECTED (16:37)` (~41 chars)
   - Not protected: `Update Arbiter - NOT PROTECTED (16:37)`
3. Move verbose detail (install date, full timestamp, reason text) into the menu's Status item, which has no length cap.

## Bug 2 — `"$ProductName:"` parses as scoped variable reference

**Symptom:**

```
At line:219 char:22
Set-Tooltip "$ProductName: status check failed"
Variable reference is not valid. ':' was not followed by a valid variable name character.
Consider using $ to delimit the name.
```

**Root cause:** PowerShell's scope syntax is `$scope:name` — `$env:USERNAME`, `$script:foo`, `$global:bar`. Inside a double-quoted string, the parser sees `"$ProductName:"` and tries to interpret `ProductName` as a scope name, then expects a variable name after the colon. Space + `status` isn't a valid variable name, so it parse-errors at runtime.

ps2exe didn't catch this at compile time because it compiles the script content as a string blob into the wrapper EXE. The script gets re-parsed inside the embedded PowerShell engine when the exe runs, so syntax errors surface only at runtime.

**Fix:** `${ProductName}:` — braces explicitly delimit the variable name, so the colon is just a literal.

## Lessons captured

1. **`NotifyIcon.Text` is 63 chars, not 127.** Always test with a real tooltip string at the deployment target, not assumed maximums.
2. **`"$Var:"` inside a double-quoted string is a parser trap.** Use `${Var}:` whenever a variable is immediately followed by a colon. The ps2exe compile step won't catch it.
3. **ps2exe is a string-embed wrapper, not a real compiler.** Treat its successful build as "syntax not catastrophically broken" — not "the script parses." Smoke-test the resulting exe before declaring done.
